# Concept Discovery 需求文档

状态：当前产品需求。更新：2026-09-27。具体交互与数据方案见[产品设计文档](产品设计文档.md)。本文描述目标和验收，不代表功能已经实现。

## 1. 产品定位

**Concept Discovery 是一个认知自动补全工具：帮助人和 Agent 在当前情境下发现已有的概念、经验和方法。**

如同输入 `conso` 时编辑器可以补全 `console.log`，人在描述模糊现象时，系统提示：“你正在说的东西，可能已经有名字了。”

例如：

> “大家都很忙但越来越慢”
> → Utilization Trap（利用率陷阱）
> → Theory of Constraints（约束理论）
> → WIP Limits（在制品限制）

这是目标体验示意。不同概念可能分别解释现象、提供分析框架或提示行动；系统应说明相关性和适用边界，用户判断是否采用。示意名称的出处和概念关系须在内容入库时核实。

核心问题：人遇到问题时，常常不知道已有知识能帮助自己，甚至不知道应该搜索什么。产品的长期价值是从情境找到值得考虑的知识。

## 2. 用户与使用场景

| 用户 | 当前需要 | 对应阶段 |
| --- | --- | --- |
| 个人知识维护者 | 把遇到的概念整理清楚，持续补充出处、场景和关系 | 第一阶段 |
| 知识使用者 | 按名称或情境线索搜索，沿关系重新找到并理解知识 | 第一阶段 |
| 不知道概念名称的人 | 描述现象，得到相关概念及推荐理由 | 后续认知自动补全 |
| 当前任务中的 Agent | 读取同一知识库，发现并应用合适概念 | 后续 CLI / Skill / API / MCP |

第一阶段面向本地单用户，优先满足维护者本人持续使用的需要。

## 3. 知识范围

统一实体称为 **Concept**，覆盖理论、思维模型、原则、方法、偏差、启发式和专业术语。“思维模型管理系统”是第一阶段的直观描述，收录范围采用广义 Concept。

每条知识应逐步回答：它是什么、什么时候想到它、应该问自己什么、什么时候不适用、有什么例子、与哪些概念相关、出处在哪里。

- 已有概念保留可追溯名称与出处；别名必须确为同义表达。
- 个人经验优先作为相关 Concept 的案例或适用提示。独立成条时明确标注个人经验和来源，不包装成公认理论。
- 案例附属于 Concept；卡片是展示方式。人和 Agent 使用同一份知识资产。
- 内容可以先存草稿，再分次补齐。中文和英文共享身份，各自维护内容。

## 4. 第一阶段：Web 知识库管理

目标是建立一套值得持续维护、可以搜索和沿关系探索的知识库，为认知自动补全提供内容基础。

| 需求 | 用户可观察的结果 |
| --- | --- |
| 人工维护 | 创建、编辑、保存草稿、补充出处与案例，关闭服务后内容仍保留 |
| 卡片浏览 | 首页直接浏览知识；卡片突出名称、简述和“什么时候想到它” |
| 详情阅读 | 能依次理解定义、场景、诊断问题、边界、案例、关联与出处 |
| 关键词检索 | 可按名称、别名和已录入的场景措辞查找；可结合标签、领域筛选 |
| 关系探索 | 人工维护有类型的概念关系，从详情连续跳转并返回原位置 |
| 双语内容 | 按当前语言浏览和检索；一种语言缺失时明确提示，不混用另一语言内容 |
| 内容维护保护 | 修订可追溯、冲突不覆盖；支持归档、恢复和受保护的永久删除 |
| 图片与来源 | 每种语言可维护多张 WebP、出处文本及可选延伸阅读链接；无图也能使用 |
| 目录概况 | 现有 Dashboard 展示真实目录数据，辅助发现待补内容 |

第一阶段以人工录入和维护为主。关键词搜索只承诺匹配已录入内容；自由改写、隐含含义和未知概念的自动补全留到后续阶段。

本阶段不新增：AI 提取与去重、Inbox 审批、批量导入导出产品界面、语义推荐入口、对外 API 产品、CLI / Skill / MCP 集成、多用户与云同步、复杂知识图谱、个性化、事件记录与结果追踪。Web 所需的本地服务接口属于内部实现。

仓库已有的推荐、Skill 与评测能力保留为后续基础；已有代码不自动扩大本阶段验收范围。

## 5. 内容与质量要求

首批使用约 12 条系统与协作主题的双语样本验证体验，具体名单见设计文档。样本需要完整的触发场景、诊断问题、适用边界、案例、真实出处及有解释价值的关系。

- 缺少来源的内容可先存草稿；占位出处不能作为样本完成的证据。
- 软件只校验出处文本是否填写，内容真实性由维护者核实。
- 普通条目不强制一次补齐全部字段，也不以 Agent 指令、配图或另一语言是否齐备阻止浏览。
- 种子样本进入隔离演示库验证，不覆盖个人知识库；现有 80 条候选清单不在本阶段批量改写。
- 旧清洗稿的 30 个 Core、Candidate Packs 和 Archive 分类不再决定收录范围或阶段目标。历史候选内容不自动导入。

## 6. 第一阶段验收

1. 在隔离数据库中完成“创建草稿 → 补齐内容 → 搜索 → 阅读详情 → 关系跳转 → 编辑 → 重启后读取”的完整流程。
2. 搜索名称、别名和已录入触发措辞都能找到对应条目；中文与英文各自生效。
3. 能从一个 Concept 连续访问相关 Concept，通过详情 URL 直接打开，并用浏览器返回。
4. 约 12 条双语样本内容和出处经人工审阅，关系可用；保留旧数据、修订及现有双语规则。
5. 归档、恢复、删除限制和并发冲突继续有效；目录统计来自真实数据。
6. 完成相应服务与浏览器回归验证。文档检查通过不能替代功能验收。

交付后的 30 天由维护者记录三类实际例子：持续补充了什么、重新找到了哪些旧知识、哪些关系帮助了理解。暂不为此建设埋点平台或虚设数值门槛。若持续维护与重新发现都没有价值，先改进内容和 Web 体验，再扩大产品范围。

## 7. 后续阶段

| 阶段 | 目标与边界 |
| --- | --- |
| 第一阶段：建立库 | 本文规定的 Web 管理、搜索、关系与内容质量 |
| 后续：认知自动补全 | 输入模糊情境，发现已有 Concept，解释为什么相关及何时不适用；允许没有合适结果 |
| 后续：工作流接入 | 按实际需要建设 CLI、Skill、对外 API、MCP；各入口消费同一知识库 |
| 更后续的候选方向 | AI 辅助整理、个性化、经验模式与应用效果反馈；有使用证据后再排期 |

认知自动补全与接入端的先后细分、推荐质量门槛及首个接入工具，在第一阶段验收后决定。本次不承诺各入口同时交付，也不要求重写已有实现。
