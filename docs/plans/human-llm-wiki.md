# 面向人的 LLM Wiki 知识闪卡改造方案

状态：功能方案，尚未实施。日期：2026-11-17。

产品定位已由用户确认：以人的理解、联系与迁移为目标，采用 Karpathy 的 LLM Wiki 模式组织知识；首版闪卡采用轻量回想与展开，暂不做复习排程。本方案以当前代码和[产品契约](../../specs/product-contract.md)为基线，只规划改造，不代表能力已经上线。

## 1. 产品目标与原文对应

**让用户选择的资料和提出的问题，持续变成可追溯、相互关联的知识闪卡，并通过回想、比较和真实应用形成自己的理解。**

模式来源为 [Karpathy 的 LLM Wiki 原始 gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。原文的重点是持久维护已综合的知识，包含原始资料、Wiki、维护规则，以及资料接纳、查询、健康检查和索引/演化日志。它是可按领域调整的模式，并未规定学习闪卡、复习算法或人的学习效果。

| 原文机制 | 本项目拟采用方式 | 本项目的适配 |
| --- | --- | --- |
| Raw sources | 保存用户实际提供的原文快照、来源信息和版本，后续模型只读 | 补充阅读与技术备份继续保留；它们不能自动充当原始来源 |
| Compiled wiki | LLM对照新资料，综合更新已有概念、比较、关联与矛盾，而非每次提问重做整理 | 核心输出采用知识闪卡；需要跨卡综合时保留主题/比较页，不把所有内容强切成小卡 |
| Schema | 编写人和LLM共用的知识维护规则：内容归属、来源引用、更新优先、冲突与维护流程 | 这是一份领域约定和操作说明，不能只用记录decision的技术状态schema代替 |
| Ingest | 用户一次选一份资料，LLM检索已有卡片并提交新增/更新提案 | 首版保留参与感，一次审阅一批差异，确认后逐项应用 |
| Query | 按问题找知识并带引用综合；有价值的回答能沉淀回Wiki | 回答保留为“推导”，经用户选择转为学习笔记或卡片更新提案 |
| Lint | 检查缺来源、失效关联、孤立卡、内容冲突和待更新项 | 用户主动触发，先列问题；语义判断与机械检查分开，不自动改写 |
| Index / Log | 知识目录负责定位，演化日志解释资料如何改变卡片 | 可从应用生成视图；知识演化日志与现有写操作回执分开 |

**人的回想、自己的解释、情境迁移是本项目的扩展。** LLM整理完成与人已经理解分开处理；AI整理内容与人的表达也有明确归属。

## 2. 当前基础与关键缺口

现状为单人桌面网站：React/Ant Design、纸感阅读界面、Markdown编辑，内部思源保存卡片，网页和CLI共用应用命令。最近一次只读核验为61张卡；本轮仅审代码和契约，没有再次读取真实库或运行浏览器。

| 功能 | 当前事实 | 建议 |
| --- | --- | --- |
| 列表、搜索、标签、日期、分页和返回上下文 | 已有，适合日常定位与管理 | **保留**；列表仍是目录，不强制变成翻卡墙 |
| Markdown编辑、图片、代码、表格、出处与旧内链 | 已有；旧复杂结构有保真限制 | **保留**；普通卡自由编辑，旧卡继续按能力阅读/局部维护 |
| 单人会话、Agent令牌、写前备份、版本检查、回执、恢复 | 已有单项保护 | **保留**并供新流程复用；不声称已具备多卡事务或整库灾备 |
| 描述AI润色 | 已有建议可修改、采用/丢弃、保存前不落库 | **保留**；复用“先建议、后采用”的模式，扩展到资料整理提案 |
| 详情阅读层次 | 旧固定字段卡有中文长文时，默认长文优先、卡片折叠 | **调整**为概念/问题先行，长文与补充阅读后展开；不删原长文 |
| 自测与知识闪卡 | 自测仅为正文；没有回想输入、答案展开或学习状态 | **补充**轻量回想，明确重新引入原契约已退出的部分交互 |
| 按问题找卡 | 已有检索、片段引用、理由、边界、应用步骤和资料缺口 | **调整**为帮助人理解、比较与应用；保留直接查看资料的路径 |
| 问答沉淀 | 仅当前标签页内存保留，刷新后清除 | **补充**用户显式保存为笔记/卡片更新提案；不自动采集全部对话 |
| 来源与补充阅读 | 有普通出处文字、可编辑阅读页；无不可变原文层 | **补充**原始资料对象、快照、版本与稳定引用定位 |
| 相关卡 | 有正文链接及旧关系归档，无现代反链索引/关系编辑闭环 | **调整**为有理由的关联，加派生反链；首版不做全库图谱 |
| LLM持续维护 | 无资料接纳→跨卡综合→审阅应用的业务流程 | **补充**持久提案、差异审阅、逐项应用和知识演化记录 |
| 健康检查 | 无知识层lint入口 | **补充**机械检查与语义问题清单，修复仍经选择 |

## 3. 使用者的四条主路径

### 读一份资料，更新已有认识

用户粘贴正文或导入Markdown/文本，填写能提供的出处信息；先保存原文快照，再明确发起整理。LLM查看已有目录和相关卡正文，给出“更新哪张卡、为什么更新、依据哪段原文、是否存在冲突”。优先更新已有卡，必要时新增概念或主题页。

审阅页呈现一次资料引发的整批差异；用户可编辑、采用或丢弃各项。应用后进入受影响卡片，看到变化与来源，不要求逐段重复确认。未采用的项目继续留作草稿；原始资料仍可独立阅读。

### 看一张卡，先回想再对照

有合适问题时，卡面展示概念名和一个问题/情境。用户可先口头回想或输入一句解释，再展开AI整理的核心解释、例子、边界、来源和关联；两种方式均可跳过回想直接阅读。

没有问题的卡仍正常阅读，不强行批量生成题目，不要求全库填写模板。短卡与长文并存：核心知识在前，推导、原文及长解释按需展开。展开内容应称“参考解释”，不将模型内容当作唯一标准答案。

“我的理解”由用户显式保存，可与整理内容并排对照。首版回想输入属于当前会话草稿，复用路由离开/重新登录后的草稿保护；刷新、关闭前提示未保存，不在后台自动落库。需要长期留存时，用户选择保存为自己的理解或应用例子。暂不新增学习评分、复习日期或提醒系统。

### 遇到真实问题，借卡片形成判断

沿用按问题找卡，可直接查看相关卡，也可比较几种解释及各自边界。用户可以先写自己的判断，再查看建议；AI反馈区分原文、应用推导和资料缺口。此步骤可选，不把每次查找都变成练习。

有价值的比较或回答可保存为主题笔记或更新提案，保留所依赖的卡片/来源版本。模型回答本身不升级成事实来源；个人经历标为个人应用记录，不能冒充外部研究结论。

### 理解变了，知道为什么变

从卡片查看新增资料、整理理由和历史采用记录；通过相关卡与反链理解关系。新资料与旧内容冲突时并列呈现两者与来源，保留“待核实”，不静默覆盖。主动运行知识检查，选择要处理的问题，再产生更新提案。

## 4. 信息结构与内容归属

保留现有“知识卡”目录、详情与编辑。增设“来源资料”“整理提案与记录”入口；问题检索仍可在知识卡目录进入。首版沿用纸感界面和桌面定位，阅读采用Read模式，编辑/审阅采用Operate模式，不借改造更换视觉风格。

| 内容 | 作用及归属 | 默认写入规则 |
| --- | --- | --- |
| 原始资料 | 用户实际选入的原文，是引用与核对依据 | 新增快照；同一来源内容更新产生新版本，不改旧版本 |
| Wiki概念卡/主题页 | LLM跨来源综合的可维护知识 | LLM产生提案，用户采用后应用；保留引用、边界及矛盾 |
| 我的理解/应用例子 | 用户自己的表达与经验 | 仅用户编辑或明确选择采用；LLM维护不能静默覆盖 |
| 目录与关系索引 | 内容的可重建导航 | 从卡片/链接派生；关联理由保留在正文，避免两套关系事实 |
| 演化日志/提案 | 解释知识为什么变化，支持恢复与审阅 | 追加事件与状态，链接原操作回执，不代替原回执 |

新卡可提供问题、核心解释、适用/边界、例子、出处和相关卡的建议结构，只显示有内容的部分。人的理解保持独立归属，不要求用户将它填成与AI整理稿相同的格式。

历史卡默认保持用户保护状态；未经核验不能标记为AI生成或来源已证实。先将明确允许维护的区域纳入LLM提案，旧固定字段卡继续按块维护。历史整篇正文的作者/来源归属不明时保持原样，不用标题猜测出处。

## 5. 技术路径建议

建议沿用思源作为Wiki卡片与人的笔记的唯一可编辑主库，继续复用应用层命令和保护机制。Karpathy的模式可以在当前产品上落实；纯Markdown/Git库重建作为备选，不列入首版。

原始资料建议新增到同一服务端私有数据根的 `sources/` 快照区，按稳定sourceId、版本、文件hash存放原文和来源清单；提案与知识事件保存在单独的私有应用元数据区。这会扩展当前“知识源仅有内部思源”的契约边界，必须在实施时明确更新契约、部署备份与恢复范围；本轮不修改现行能力描述。原件与衍生卡片各有单一权威，来源文件不会成为另一套可编辑卡片库。

```mermaid
flowchart LR
  A[用户选入的原始资料] --> B[只读来源快照与版本]
  B --> C[LLM对照已有知识提出更新]
  D[现有Wiki卡片与来源] --> C
  C --> E[用户审阅差异与引用]
  E --> F[逐项受保护写入]
  F --> D
  D --> G[阅读·回想·比较·应用]
  G --> H[我的理解与应用记录]
  H --> I[用户选择形成更新提案]
  I --> E
```

### 必须补齐的实现约束

1. **来源版本与引用。** 引用持久绑定sourceId/version/原文定位及hash；抽取文本也记录版本，引用定位在该不可变表示上。现有ask临时e编号只用于当次回答，不承担长期溯源。持久引用只能证明版本和位置可核对，不能自动证明某段原文支持某个解释，语义仍需审阅。旧卡只有URL时标注无原文快照，不回填为已核验。仅有链接的新输入先作为待补资料，未取得原文不能开始编译。
2. **保护人的内容。** 提案指明基线revision/块指纹与目标区域，归属在应用层受校验；前端隐藏区域不能充当权限边界。人的理解、例子和原有保护块变化时拒绝旧提案，重新读取并生成差异。
3. **持久提案与逐项应用。** 同批对同一卡的更新先合并为一个提案项，记录来源、目标、基线、变更、理由及其op_id；用户采用后逐卡/块写入并读回。每项请求及op_id先持久化，再执行写入；进程崩溃或重启后先查原操作回执并读回卡片，再补知识日志或继续未执行项，不能只根据提案状态重复写。取消停止尚未发起项，已发出的项仍按原回执核对。整体可能部分完成，界面明确已应用、冲突、未知及未执行；未知先查原回执，不换ID盲重试。单卡保存本身也可能部分完成，沿用现有受保护恢复。
4. **依赖与恢复。** 新建卡先取得真实ID，再应用依赖它的链接；前置项失败则暂停依赖项。首版不承诺整批同时可见或失败全回滚；如需整批原子发布，另做版本快照/发布指针方案。恢复必须按当前版本保护后续用户修改。
5. **索引与知识日志。** 目录与反链可重建，并且只包括当前知识范围；来源、提案不能混入概念检索伪装成卡片。日志记录资料接纳、卡片更新、用户采用与lint处理及状态；部分应用逐项记录，不把整批标为已完成。日志不存密钥或原始私有对话。
6. **模型调用边界。** 用户显式发起整理、查询或语义检查；告知模型目的地与所选原文、卡片片段范围。原文中的操作指令作为资料处理。接口不支持相应格式或鉴权失败时停止批处理，先用不含私有材料的最小请求核验能力。历史实验的一次性外发授权和临时凭据不成为新功能的持久授权。
7. **数据管理。** 备份覆盖思源workspace、sources、提案/知识事件、operations及私有配置；在隔离目录演练整体恢复并验证跨域引用。不可变指应用不覆盖旧快照及hash检测，不宣称管理员无法修改的存储级WORM。用户有意删除来源是独立操作，应先显示受影响引用并保留明确失效标记，不能静默清理。

当前`get-document`、`cardScope`和底层可写目标主要限定concept/article。新来源/提案采用各自应用入口与鉴权/范围校验，不通过扩大通用卡片写权限绕过隔离；若改为思源内存储来源，也必须显式设计新类型的读取、搜索和写入边界。

## 6. 分期实施与验收

### P1：完成一个小规模端到端闭环

首版范围包括：知识维护规则、文本/Markdown来源快照、一次一份资料的跨卡更新提案、差异审阅/逐项采用、来源追溯、核心卡片先行阅读、已有问题的轻量回想/展开、我的理解显式保存、基本目录与演化记录。

建议按依赖依次交付，不把第一期变成全库重写：

| 实施片段 | 内容 | 可观察验收 |
| --- | --- | --- |
| P1a 资料与归属 | 文本来源快照/版本/引用定位；保护原有卡与人的内容；落地维护规则 | 重复资料可识别；来源更新保留旧版本；未经确认的旧内容保持原样 |
| P1b 编译与审阅 | 检索已有卡、跨来源整理、持久差异提案、逐项应用与日志 | 一份资料能更新已有卡并提出有理由的关联；冲突、未知、部分应用可恢复，不覆盖后续修改 |
| P1c 阅读与回想 | 调整旧长文优先、问题展开、会话回想草稿、显式保存我的理解 | 不看解释能先尝试回想；无问题仍可读；长文/图片/来源保真；人的笔记不会被整理覆盖 |
| P1d 小样闭环 | 用户选3份真实资料、约10张相关卡，其中纳入旧格式/长文卡 | 走通资料→提案→采用→阅读回想→自己的理解写回；用户能找到每次更新的依据与理由 |

范围不包含网页自动抓取、PDF/OCR/音视频提取、自动批量收集、复杂图谱、自动学习评分和SRS。来源的首版输入为实际提供的Markdown/文本及元信息；附件仍按现有规则保留，复杂抽取后续扩展。

P1a实施任务同时冻结单份资料大小及模型输入预算，分别约束原文保存与整理调用。超限应明确拒绝整理或让用户选择片段，保留完整原件并显示尚未整理的范围；禁止静默截断后将整份资料标为已处理。来源正文、目录及相关卡共同占用调用预算，不能只限制单一字段。

### P2：让查询与维护真正积累

补充问答保存为笔记/更新提案、跨卡主题/比较页的轻量入口、关系理由与反链导航、知识lint问题清单、来源新版本影响提示。更新优先于重复建卡，矛盾保留双方来源和适用条件；语义lint仅提示，不保证自动判断真伪。用户可按需选取待处理项，首版不添加后台自动维护。

主题/比较页优先复用普通Markdown文档，加明确导航分类；不把当前只作为卡片附属阅读的article直接当作已具备的独立主题页。其列表、检索与链接范围在P2实施任务中一起验收。

验收：有价值的查询刷新后仍能从用户选择保存的位置找到；卡片更新后可追踪相关来源与受影响关系；机械失效与待核实语义问题被清楚区分；修复按提案流程完成。

### P3：依据人的使用结果扩展

验证后再决定多格式来源采集、跨主题探索、较大规模索引、用户主动学习记录或完整复习系统。MCP按实际接入需求另评估，保留CLI；它不作为人的学习体验前置条件。移动端、多人协作、公开知识社区、全库关系图及存储重建均不进入当前改造。

## 7. 人的效果如何验证

[上轮三组实验](../../tasks/0013-node-decision-experiment.md)测量模型建议，不是人的学习效果，不能作为本次认知收益的正反证据。

小样验证围绕维护者自己的真实问题，事先保留原有解释与实际任务，再观察：

- 能否用自己的话解释概念、依据及不适用条件，指出仍不懂的部分。
- 展开前尝试回答，展开后识别理解差异，并写出自己的例子或修正。
- 在隔几天的新情境里，能否主动想到相关概念，说明为何适用或拒绝使用。
- 能否从一张卡沿有理由的关联找到另一个角度，解释关系而非只认出术语。
- 新资料是否让既有卡片及人的理解发生有依据的更新，维护步骤是否愿意日常重复。

这是一位使用者的小规模使用观察，不计算“全体用户认知提升率”。可将部分资料先按原有阅读方式使用、部分走新流程，并在看结果前记录具体问题和判断标准；不把读卡次数、卡片数量、模型评分或一周自我感受当作已证明的学习效果。延后回访属于试用安排，不等于在产品中开发提醒或排程。

## 9. 首版边界与需要后续验证的选择

- 已确认：面向人、Karpathy模式、轻量回想与展开、暂不排程。
- 本方案建议：保留思源Wiki主库，原文快照新增私有来源区；先文本/Markdown、一次一份资料；提案先审阅后逐项应用；人的理解独立保护。
- 待小样验证：问题是否帮助回想、差异审阅负担、概念卡与主题页比例、哪些跨卡关联值得维护、来源格式扩展优先级。
- 当前未实施：本方案中的来源库、LLM编译、反链、轻量回想、提案、知识日志与lint。现行契约和项目清单继续表示现状，后续实现同步更新，不提前宣称完成。

本轮方案基于源码/契约审计与原文核对，未做浏览器实测、真实资料导入、真实库写入或新的模型实验。实施从P1a开始，以P1d完整闭环作为首个产品验收单位。
