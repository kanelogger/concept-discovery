# 任务流程与交接

目标：从仓库入口能知道当前任务、实际结果和下一步，避免同一信息重复维护。

各阶段的输入和完成条件见[从需求到验收](#从需求到验收)。需要独立判断时，使用[审阅材料与判定](#独立审阅的材料与判定)准备交接包。

## 开始与执行

1. 开始（start）：检查工作树，读取根 `AGENTS.md`、[执行环境](../project.yml)、本工作流和[状态文件](../workflow-state.json)。有任务时读取 `task_file`，恢复目标、边界、验收与未决事项；新请求不自动续做旧任务。按本机索引 `.agents/context/index.json` 读取 `commands` 等当前所需条目。没有本机索引时直接读 `package.json` 及相关规则、产品契约和实现。
2. 计划（plan）：新实现任务在 `tasks/` 创建独立编号文件，参考[任务模板](task-template.md)；只读导读不必建档。按影响范围读取产品契约、规则和实现入口（如 `business.draft`、`business.save`），核对来源冲突；重要决策记录简短理由、依据和反证条件。按改动风险查阅[经验库](../LESSONS.md)，对照[独立审阅与问题闭环](#独立审阅与问题闭环)安排方案审阅。未知只限制受影响动作。
3. 实施（implement）：保留已有和并发修改，必要时明确文件所有权；按需读取受影响模块与规则。来源、代码或原有假设变化时重读相关材料并调整计划；稳定事实先写回所属文档。常规可逆工作持续完成，方向性歧义无法从上下文解决时询问用户。
4. 验证（verify）：重取本任务完成标准、`commands` 与 `verification` 所指的真实入口，按[验证规则](../rules/testing.md)执行相称检查；记录输入、环境、实际结果、失败与未覆盖范围。结构检查和业务验证按各自范围记录；按[独立审阅与问题闭环](#独立审阅与问题闭环)审阅最终差异和证据。
5. 交接（handoff）：更新任务证据、决策、审阅结果、未决事项和下一步。
   - 检查证据是否支持跨任务复用的新发现。符合条件时写回[经验库](../LESSONS.md)，记录触发条件、已核实原因、纠正方法、适用范围和可回查证据；同类条目合并并补充证据或边界，待证实观察留在本任务。
   - 先更新稳定知识归属的文档，再按变化文件和本次已用 key 核对索引，仅增量维护受影响项。直接引用变化时重读正文，依赖过期时重证结论；未索引文件按实际影响核对。
6. 审查差异、清理本轮资源并同步 `workflow-state.json` 后，按 Git 规则提交任务相关改动，将阶段设为 `complete`；新任务切换指针并保留旧记录。状态只存当前指针、阶段、日期、摘要与必要下一步，详细证据只写任务文件。

同一任务中已读且版本未变的材料可复用。用户明确调用技能且工具可用时，按技能的 `context node` 读取相应节点，显式附本次 key、变化文件及任务路径；交接用 `context check` 检查关联项，再以 `context update` 增量维护。普通任务或工具不可用时，直接按索引读取段落或字段并做同等来源核对，不依赖技能安装或 hooks。工具返回未覆盖项时继续定位所需来源，不把未找到当作没有规则。

### 角色配置与调用

需要委派时，由当前任务执行者读取根[角色配置](../agents.yml)，通过当前执行环境可用的方式匹配角色。规划用 `planner`，实施与修复用 `implementer`，方案审阅、最终审阅与修复后复核用 `reviewer`。按现有触发条件选择角色，日常任务可由当前执行者自行规划和实施。

`agent` 和 `model` 分别按本次任务指定、角色配置、`defaults`、执行环境默认值的顺序取值。省略或 `null` 时继续继承，当前配置使用执行环境默认值。委派时依次组合 `defaults.prompt`、角色的 `prompt` 与本次需求、验收、适用规范、证据和授权范围，显式传入材料及路径。角色配置由执行者读取，委派能力和授权以当前环境为准。

### 独立审阅与问题闭环

- 首次接入，或涉及权限和写保护、持久数据迁移或恢复、跨模块契约、会影响验收结论的验证入口和规则时，在实施前审阅方案，在交付前独立审阅最终差异、验证结果和未覆盖范围。方案审阅者未参与方案编写，变更审阅者未参与实施。
- 显式用全新上下文启动每次审阅与复核（如 `fork_turns: "none"`），提供原始需求与验收、适用规范、可读材料、待审方案或最终差异、验证证据及只读授权范围。请审阅者独立核实发现的位置、触发条件和影响，结果回填本任务。独立审阅或上下文隔离不可用时，记录自查覆盖、限制及未解决风险。
- 逐项核实发现并记录处置及依据。每次修复后重跑受影响的检查，再请未参与修复的审阅者复核相关发现和最终差异；交接时保留未解决、未证实或未覆盖项及影响。

## 状态约定

`workflow-state.json` 是交接入口，不是权限系统、锁或调度器。基础字段为 `schema_version`、`task_id`、`task_file`、`phase`、`updated_at` 和 `summary`，可按需附 `next_actions` 或 `blockers`。

| phase | 含义 |
| --- | --- |
| `idle` | 无当前任务，任务指针为 `null` |
| `planning` | 明确目标、范围和验收 |
| `implementation` | 实现已授权工作 |
| `verification` | 验证、审查和清理 |
| `blocked` | 在任务中说明阻塞原因和解除条件 |
| `complete` | 当前范围完成，任务中有实际结果和遗留事项 |

`task_file` 使用 `tasks/<task_id>.md`；日期使用有效 ISO 日期或带时区的时间。`npm run validate`检查入口路径、命令引用和基础状态结构，不证明功能正确或命令实际运行。旧的 `required_checks` / `verification` 字段兼容保留，不再作为完成门禁。

## 事实与长期记录

- 产品边界放 `specs/`，实现事实直接引用源码、配置和测试。
- 本轮进度、验证、失败和取舍放任务文件；跨任务决定进入长期文档，有证据的复用经验进入[经验库](../LESSONS.md)。
- 原始材料注明状态，不把草稿或历史记录当作当前能力。
- 结束时只清理本轮有归属记录的临时资源，保护正式资料；失败和残留写明恢复方法。

从 `AGENTS.md` 出发应能回答：当前产品状态、任务是否完成、如何运行检查、尚未决定什么，以及下一步是什么。

## 从需求到验收

本节补充[开始与执行](#开始与执行)各节点的完成条件。新实施任务使用同一份编号任务文件，短任务简记，临时分工由主执行者汇总。按需要隔离共享文件、索引和服务。委派前显式选择全新上下文，给出原始目标、所需材料或可读绝对路径、授权与可写范围、验收和回报位置。无法隔离时，由当前执行者推进可完成的部分。

1. **确认输入。** 核对分支、基线、工作树归属、实际配置和最新需求讨论，查明现成补丁与新增限制。恢复任务时重新确认输入、上次完成步骤、当前资源和下一步。行为变化要从[现行产品契约](../specs/product-contract.md)沿链接读到对应条款，将出处、触发条件、操作和可观察结果写入验收。缺失或冲突的条款记录在本任务。
2. **建立对照。** 缺陷从报告者实际使用的入口、输入和环境复现，用能区分可能原因的检查取证。不能复现时记录差异及未知项。计划写清用户可见变化、实现位置、调用方、风险与关键假设。验收逐项给出场景、预期、验证办法和证据位置。涉及迁移时列出执行顺序、回滚或补偿；外部调用先核对副作用，在隔离环境验证。依[独立审阅与问题闭环](#独立审阅与问题闭环)核实计划发现后再实施。
3. **检查整条调用链。** 搜索同类判断、其他入口和旧行为的调用方；沿项目既有惯例修正并清理本次产生的失效引用。独立问题另记。保留兼容路径时写明适用条件与后续处置；配置或迁移核对旧数据、用户覆盖及失败恢复。职责、契约、状态或异常行为有变化时，同步所属说明及规格的验收条件。每项差异都应能回到原始目标。
4. **验证最终输入。** 按[验证规则](../rules/testing.md)从用户输入跟至实际输出、持久化与副作用，比较前后行为。核实发现的触发条件和影响；证据不足时补取证据。失败保留日志，区分基线问题和本次引入的问题，记录复现与处理状态；连续失败且无线索时保留现场。本次引入的失败须修复并复验后再交付。项目要求的检查缺失或失败时，记录缺口及影响，不得宣布已达到合并或发布条件。最终范围触发独审时送审最终差异和实测结果；修复后跑受影响检查并复核。审后输入变化须重验受影响部分。
5. **留下可接手的证据。** 在唯一任务文件记录目标、前后行为、基线与待交付版本（未提交时标明差异或快照）、环境和隔离方式、检查输入、预期与实测、证据位置。修复任务注明旧实现对照或替代证据。分别记录失败、跳过、取消、未运行、审阅者及结论和遗留事项。交付前读完整差异和候选新增文件，核对敏感内容、生成物及本机状态。任务记录归档后保持可访问；长期取舍记入项目决策记录。按[Git 规则](../rules/git.md)核对暂存范围，提交后读回文件清单与说明。冲突解决、重定基或组合变化后重验最终输入。
6. **复盘与演练。** 有证据的跨任务发现按[经验库](../LESSONS.md)回写。稳定且可机械判断的问题可接入已有检查，用反例证明守卫会失败。用实际开发任务检查规则能否支持实施、验收与归档；需要跨会话接手时，在全新上下文从根入口恢复，记录版本、环境和中断点。

### 涉及合并或发布时

在相应授权范围内核实目标基线、待合入版本和审阅版本。核对最终组合已通过项目必需检查，采用版本匹配或等效方式防止新推送意外合入。发布前确认版本无冲突、待发布版本与验证输入一致、必需检查已成功；发布后读回目标版本的实际产物、下载或部署入口与更新渠道。外部构建与发布有界等待，部分成功分别记录并恢复。

## 独立审阅的材料与判定

[项目审阅触发条件](#独立审阅与问题闭环)也适用于复杂方案。普通短任务按风险自查。每次审阅或复核在调用前核实上下文隔离及模型选择能力。能力和授权允许时优先请不同 Agent、不同模型判断；向各审阅者提供一致的材料。记录实际执行者、会话、可核实的模型以及受审版本或快照；模型未知时如实写明。同模型的独立新会话可履行独审，异构审阅需要实际使用不同模型。

- **共同材料。** 给出原始需求、验收、适用规范、计划或最终差异、相关实现、工作区与输入版本、实测和工具输出、未覆盖项与风险。提供原文或可读绝对路径，明确只读职责、回报位置和完成条件。审阅者直接核对来源；有争议时可用新反例、实际测试或其他新增证据判断。
- **计划审阅。** 未参与编写的审阅者从真实调用方和现场约束核对遗漏路径、规则冲突、不可回滚步骤、验证不足及未经证实的假设，说明具体位置、触发条件、影响与需修正之处。实施者逐项查证并修订计划。
- **最终审阅。** 未参与实施或修复的审阅者从输入追踪至输出、持久化与副作用，核对公开契约、并发、恢复、错误和边界路径，检查测试污染、假阳性及覆盖缺口。按严重度记录位置、触发条件、影响及证据。证据不足的发现标为待证实，无发现时写明覆盖范围和剩余风险。
- **处置与复核。** 修复者逐项记录接受、不接受或待核实及理由，自行依据需求选择修复办法。复验后把相关发现、更新后的最终差异与新证据交给未参与修复的审阅者。输入变化时重做受影响的审阅与验证，并在任务内记录结论、依据和缺口。
